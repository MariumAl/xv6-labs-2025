Q2:
The optimization maps a read-only page at the address USYSCALL into each process’s address space.
This page holds a struct usyscall that is initialized with the process’s PID.
The user-space function ugetpid() can then read the PID directly from this page instead of making a regular system call, avoiding the overhead of crossing the kernel boundary.
Similar optimizations could be applied to other system calls that return small, read-only pieces of kernel state, such as getppid() or time(), to further reduce overhead.

Q3:

The vmprint() function in vm.c displays the complete three-level page table used by RISC-V.
Each printed line represents a valid page table entry (PTE) at a particular level, showing the virtual address it maps, the PTE’s flags, and the corresponding physical address.

In my output, the root (top-level) page table was located at 0x0000000087f52000.
The entries beneath it show valid mappings for this process’s address space.
The indentation (.. ..) reflects the depth in the page-table hierarchy.

For example, some lower-level entries were:

.. .. ..0:  pte 0x0000000021fd381b  pa 0x0000000087f4f000
.. .. ..1:  pte 0x0000000021fd2c17  pa 0x0000000087f4c000
.. .. ..2:  pte 0x0000000021fd2807  pa 0x0000000087f4b000
.. .. ..3:  pte 0x0000000021fd2417  pa 0x0000000087f4a000


These leaf pages correspond to the user-space segments of the program — such as the code (text) segment, data/BSS sections, and the stack.
Each leaf-level PTE directly maps a virtual page to a real physical memory page used by the process.

The PTE flags (e.g., 0x1B, 0x17, 0x07) indicate combinations of permissions:

PTE_V – valid

PTE_R – readable

PTE_W – writable

PTE_X – executable

PTE_U – accessible from user mode

For instance:

0x1B → valid, user, readable, writable (typical for data pages)

0x17 → valid, user, readable, executable (typical for code pages)

0x07 → valid, readable, writable, executable (e.g., stack or special pages)

These correspond to the mappings seen in print_pgtbl(), which showed a linear mapping of user virtual addresses (e.g., from 0x0 up to 0x4000).

At the higher virtual addresses (close to the top of the address space), we find entries like:

.. .. ..509:  pte 0x0000000021fd5413  pa 0x0000000087f56000
.. .. ..510:  pte 0x0000000021fd5807  pa 0x0000000087f57000
.. .. ..511:  pte 0x000000002000180b  pa 0x0000000080006000


These are kernel-mapped pages that appear in every process’s page table:

The trapframe page, which stores register states during system calls and interrupts.

The trampoline page, which contains the small assembly routines for entering and exiting the kernel.

The flags for these typically include PTE_V (valid), PTE_R (readable), and sometimes PTE_X (executable, for the trampoline), but usually exclude PTE_W since they map code or fixed kernel data.

Compared to the simpler, linear view shown by print_pgtbl(), the vmprint() output exposes the true three-level structure used by the hardware for address translation.
This gives a clearer picture of how the operating system organizes and protects both user and kernel memory spaces.
